Robot Agent：自主决策、技能组合与持续进化

这部分不是通用 LLM Agent 教程。目标是理解并设计一个以 Agent 为决策核心、以异构 Skill 为执行能力、能够通过经验持续改进自身技能的机器人系统。

最终目标：Agent 决定做什么，Skill 负责把事情做好

Agent 接收任务和环境状态，判断下一步需要什么能力；它可以调用长时序 VLA、World Model、视觉感知、运动控制或 Code Policy。复杂技能还可以继续组合子技能。执行结果和经验返回 Agent，用于继续决策或改进技能。

01先建立正确的系统边界

核心是 Agent-centric，而不是双系统必须并行。System 1 / System 2 可以作为同一个 Agent 的快速与深度推理模式；系统是否启用深度推理，由任务复杂度、风险和不确定性决定。

Agent · 决策核心

理解目标、维护任务状态、选择 Skill、检查进度、处理异常。简单情况走快速路径，复杂情况进入深度推理。

→

Skill Runtime · 执行能力

调用 VLA、World Model、Code Policy、SAM/3D 感知、MPC 等能力；接收执行状态和可信结果。

VLA Skill可持续执行较长时序任务，内部处理观测—动作闭环，在子目标、异常或终止条件处回报。
World Model Skill预测未来状态、比较候选动作、进行反事实推演；不要求直接输出控制动作。
Code Policy Skill可执行程序或控制器，能够封装感知、策略、MPC 和恢复逻辑，并由经验驱动更新。
Perception / Geometry SkillSAM、检测、深度、点云、位姿估计和抓取候选生成，为决策提供结构化状态。
重要边界：Agent 不需要接管每个控制周期。高频闭环留在 VLA、Policy 或实时控制器内部；Agent 在任务级、子目标级和异常节点做决策。

System 1 / System 2 不应被写成两个固定 Agent 的强制协作协议。先掌握单 Agent 的决策闭环，再把快速响应与深度推理作为可选调度策略加入。

02Agent 如何真正做决策：从一次 Tool Call 到闭环任务

先不要把 Agent Loop 理解成一句“观察—思考—行动”。工程上最重要的是：每一轮决策拿到什么状态、允许做出什么动作、动作会改变哪些状态、什么时候必须重新观察，以及由谁判定任务成功。

2.1 Agent 看到的不是完整世界，而是一个有边界的决策上下文

机器人环境在时刻 t 有真实状态 x_t，但 Agent 通常无法直接读取它。相机图像、关节状态、力觉、工具返回值只是观测 o_t。历史动作和观测可以帮助估计当前状态，但历史本身也可能过期：机器人移动了、物体被碰动了，旧的物体位姿就不再可信。

因此 Agent 的输入最好被组织成显式的 World State / Belief State，而不是不断把所有聊天记录拼进 Prompt。一个实用状态可以分为四块：任务状态（目标、子目标、完成条件）；场景状态（物体、位姿、可达性和置信度）；机器人状态（底盘、关节、夹爪、当前控制模式）；执行状态（正在运行的 Skill、已完成步骤、最近一次环境变化和失败原因）。

WorldState = { task: { goal: "打开右侧柜门并取出药盒", subgoal: "建立把手接触", status: "executing" }, scene: { handle_pose: {frame: "world", xyz: [0.42, -0.18, 0.91]}, handle_confidence: 0.87, door_angle: 0.12, observed_at: 1710000000.0 }, robot: { base_pose: "...", tcp_pose: "...", gripper_width: 0.04 }, execution: { active_skill: "approach_handle", skill_status: "succeeded", last_receipt: "contact_established" } }

这里的时间戳和坐标系不是装饰字段。observed_at 用于判断感知结果是否陈旧；frame 用于防止把相机坐标系下的点直接交给要求世界坐标的运动规划器。没有来源和置信度的数字，不应该被 Agent 当作确定事实。

2.2 一轮 Agent 决策应该输出什么？

不要让模型每轮输出一段自然语言计划，再让另一个程序猜测它想做什么。更稳妥的方式是将每轮决策约束成结构化命令。一个最小决策可以是：调用一个工具、向人询问、报告状态，或者明确结束任务。模型给出的是“下一步意图”，Host/Runtime 再验证参数、权限和副作用，最后才执行。

# 示意：模型输出的决策，不是机器人底层动作向量 decision = { "kind": "tool_call", "name": "move_to", "parameters": { "target_pose_ref": "world_pose_018", "speed_profile": "approach" }, "reasoning": "已定位把手，需要先移动到预接触位姿" } # Host 负责校验工具是否存在、参数是否合法、 # 当前状态是否允许执行，以及是否需要安全检查。 result = runtime.dispatch(decision)

这里必须区分四个对象：AgentCommand 是模型提出的决策；Tool 是 Agent 可以调用的接口；AtomAction 是会改变物理世界的原子动作；EnvAction 是适配器或日志层使用的环境协议。把它们都叫 Action，会导致“模型决定调用工具”和“机器人执行关节控制”混为一谈。

2.3 为什么物理动作后要重新观察？

只读感知通常可以批量执行，因为它们不会改变环境；物理动作则不同。一次 move_to 可能碰到物体、改变接触关系，甚至造成目标位姿变化。若 Agent 紧接着基于旧观测再发一个动作，第二个动作的前提可能已经不成立。

因此一个稳健的闭环是：读取观测 → 选择一个物理动作 → 执行 → 获取执行回执 → 重新观察 → 更新 World State → 再决策。这里不是说所有机器人系统都必须一次只发一个低层控制周期，而是说任务级 Agent 不应在没有新证据的情况下连续假设多个世界变化动作都按计划发生。长时序 VLA 可以在 Skill 内部执行多个动作块，但它必须有自己的观测与反馈机制。

OpenETA 的真实设计：其主 Planner 每轮选择一个 tool_call 或 response；世界改变类 AtomAction 单独执行，并要求后续重新观察。只读查询或规划工具可以在受限条件下批量调用。这是把闭环原则落实到 Runtime 合同，而不是仅仅写在 Prompt 里。

2.4 Agent Loop 的最小实现

async def run_task(goal, runtime, max_turns=80): state = await runtime.observe_world() memory = await runtime.load_task_memory(goal) for turn in range(max_turns): context = build_context( goal=goal, world_state=state, memory=memory, available_skills=runtime.skill_registry.describe() ) decision = await planner.next_decision(context) decision = validate_schema_and_permissions(decision, state) if decision.kind == "response": if decision.status == "task_complete": return verify_terminal_state(goal, state) if decision.status == "ask_human": return await runtime.request_human(decision) result = await runtime.execute(decision) memory = update_episode_memory(memory, decision, result) # 世界改变后必须刷新观测；不要只相信工具返回的文本 if result.world_may_have_changed: state = await runtime.observe_world() else: state = merge_read_only_result(state, result) if result.status in {"failed", "uncertain"}: state = await diagnose_and_refresh(state, result) return {"status": "timeout", "last_state": state}

这段伪代码刻意把 planner、runtime、verify_terminal_state 分开。模型负责选择下一步，Runtime 负责执行合同，环境或独立验证器负责判断事实。实际系统还需要取消、超时、重试预算、幂等键和安全限制，但这些应作为 Runtime 能力，而不是要求 LLM 每次自己记住。

03Skill、Tool、Policy 到底有什么区别？

这是设计 Robot Agent 时最容易混乱的概念。把四者区分清楚，才能决定哪些能力暴露给 Agent，哪些细节留在技能内部。

四层概念对照

对象它是什么例子谁负责
Policy给定条件，产生动作或动作分布的映射π0.5、Diffusion Policy、RL Policy策略模型/控制算法
ToolAgent 可调用的原子接口sam3、observe、move_toTool Handler / Host
Skill面向目标的可复用能力，可由多个工具与 Policy 组成pick_object、open_doorSkill Runtime / Skill 实现
Agent根据目标和状态选择下一步能力，并决定何时继续或结束任务规划与技能路由Planner / Reasoner

3.1 Skill 是一个有契约的长时序能力

例如 pick_object 不是一个“抓取”函数就结束了。它可能先做目标确认、计算抓取位姿、检查可达性、执行接近、闭合夹爪、抬起物体，再验证是否抓稳。Skill 对 Agent 暴露一个稳定接口，但内部可以使用 SAM、点云、VLA、MPC 和多个原子 Tool。

Skill 的输入应表达任务目标和约束，而不是把所有底层参数都塞给 Agent。输出应包含执行状态、真实证据和可恢复信息，而不只是自然语言总结。一个可执行合同至少包括：

SkillSpec: name: pick_object input: object_ref: ObjectReference destination: Optional[Pose] constraints: MotionConstraints preconditions: - target_is_localized - robot_is_ready runtime: mode: long_running supports_cancel: true timeout_s: 45 checkpoints: - grasp_candidate_selected - pregrasp_reached - gripper_closed - object_lifted output: status: succeeded | failed | uncertain evidence: GraspEvidence failure_code: Optional[str] recovery_options: List[SkillReference]

3.2 Skill 生命周期不是函数返回值

长时序技能需要异步生命周期。accepted 表示 Runtime 接受了请求；running 表示执行中；yielded 表示到达检查点并交还控制权；succeeded 表示技能自己的完成条件成立；failed 表示失败；cancelled 表示被取消。还要区分 uncertain：系统没有足够证据证明成功，也没有证据证明失败。

为什么要有 yielded？例如 VLA 正在执行“把物体放入篮子”，它可能连续运行十几秒；如果每个动作块都让 Agent 重新推理，延迟和成本很高。但如果完全不汇报，Agent 又无法在物体滑落、障碍出现或子目标完成时介入。检查点就是技能与 Agent 之间的控制交接点。

注意：accepted / running / yielded / succeeded / failed / cancelled / uncertain 是本课程建议采用的通用 Skill Runtime 状态合同，不是所有机器人框架共同遵循的标准枚举。实际项目可以采用不同名称，但必须明确状态含义、合法转换、超时和取消语义。

3.3 为什么不把 Skill 自动展开成隐藏动作序列？

一种做法是 Agent 调用 open_door，Runtime 自动执行一串隐藏的 move_to、gripper_close 和 pull。这种做法简单，但如果隐藏执行过程没有观测、日志和中断机制，Agent 就无法知道动作是否按预期发生。OpenETA 的设计选择是：Skill 文档可以提供可读的操作指导，但不会自动变成隐藏工具调用；真正执行仍通过明确的 Tool Call 和回执进行。这牺牲部分便利性，换取可追踪和可验证性。

3.4 一个 Skill 可以递归包含子 Skill

open_door_skill ├── locate_handle_skill │ ├── sam3_tool │ └── camera_pose_to_world_tool ├── estimate_hinge_skill │ ├── point_cloud_tool │ └── geometric_fit_tool ├── predict_interaction_skill │ └── world_model_skill ├── execute_pull_skill │ ├── long_horizon_vla_skill │ └── compliant_mpc_skill └── verify_open_skill ├── door_angle_estimator └── force_state_check

层级 Skill 需要避免无限递归和不透明依赖。实践中可以用 Skill Registry 记录名称、版本、输入输出 Schema、依赖、适用机器人、运行预算和验证器；Agent 先选择高层能力，Skill Runtime 再决定内部组合。若 Skill 失败，应返回可定位的阶段和证据，而不是只返回 success=false。

04长时序 VLA：Agent 调用的是执行过程，不是一个动作块

你已经熟悉 π0.5、Action Chunk 和 RTC，因此这节不重复讲 VLA 网络结构。重点是如何把一个会持续闭环的 VLA Policy 封装成 Agent 可以委托的执行型 Skill。

4.1 三种不同的控制时间尺度

层级典型频率/时长主要职责是否调用 LLM
实时控制数百 Hz 至 kHz（依平台）关节伺服、阻抗、力矩、安全限制否
Policy / VLA数 Hz 至数十 Hz；持续数秒或更久观察、生成动作块、执行、滚动修正通常否
Task Agent事件触发或子目标级选择 Skill、判断进度、异常恢复、任务重规划需要时

频率不是固定标准，取决于模型推理、机器人控制接口和任务。真正的原则是时间尺度分离：LLM 不进入实时控制回路；VLA 不必承担整项任务的目标分解；底层控制器不负责理解自然语言任务。

4.2 一次委托如何完成一个长时序子任务？

Agent → SkillRuntime.start( skill="pick_and_place_vla", goal={ "object": "blue_medicine_box", "destination": "basket_A" }, completion={ "object_inside": "basket_A", "gripper_state": "open" } ) Skill Runtime: load policy + robot adapter while not terminal: observation = robot.observe() action_chunk = vla.predict(observation, goal) controller.execute(action_chunk) event = monitor.check(observation, action_chunk) if event == "subgoal_reached": yield checkpoint if event == "unexpected_contact": yield needs_replanning if event == "object_dropped": return failed return succeeded + evidence

Agent 调用一次 Skill，并不是让 VLA 开环跑完整段动作。VLA Skill 内部仍然需要观测更新、动作 Chunk 执行和必要的重预测。Agent 只在 Skill 完成、遇到异常、达到关键子目标或需要额外能力时重新介入。

4.3 旧 Chunk、新 Chunk 与 Agent 介入不是一回事

RTC 解决的是动作预测更新时，旧动作块和新动作块如何衔接，减少切换造成的不连续；它本身不解决任务级决策。Agent 的任务是判断是否仍在执行原子目标、是否需要改变目标、是否需要调用其他 Skill。即使 RTC 把轨迹衔接得非常平滑，也可能平滑地执行了错误目标；反过来，Agent 的高层决策正确，也不代表动作 Chunk 没有抖动。

因此评估至少分三层：动作层看轨迹连续性、近中远端误差和控制约束；技能层看子目标完成率、执行时间和失败类型；任务层看最终成功率、重规划次数、人工介入和跨场景泛化。不能只用 VLA 的单步预测误差来评价 Agent 系统。

4.4 何时把控制权交回 Agent？

  • 正常完成：Skill 返回成功证据，Agent 更新任务状态并选择下一个 Skill。
  • 子目标完成：例如门已打开 30°，需要重新观察，再决定是否继续拉开或伸手取物。
  • 环境异常：接触力超限、目标消失、物体掉落、底盘偏移，Skill 暂停并请求重新规划。
  • 能力不足：VLA 多次失败，Agent 改用几何工具、World Model 或 Code Policy。
  • 不确定：Skill 无法证明成功，Agent 调用独立验证 Skill，而不是直接宣布任务完成。
对你的系统，一个很实用的设计是：VLA 负责长时序连续操作；Agent 负责子目标切换、异常路由和策略替换。不要让 LLM 逐 Chunk 指挥，也不要让 VLA 独自承担所有任务规划。

05World Model 作为 Skill：预测结果如何真正影响决策？

把 World Model 包装成一个 API 并不难，难的是明确它预测的变量、适用范围、不确定性，以及 Agent 根据预测结果到底改变了什么决策。

5.1 先区分三类模型

类型输入输出对 Agent 的价值
视频生成模型图像、文本或动作条件未来视频帧直观预测，但未必提供可执行状态或准确动力学
潜空间动力学模型潜状态、动作未来潜状态/奖励/终止可快速比较候选动作，需确认潜变量与任务相关
结构化物理/交互模型物体状态、接触、动作参数位姿、接触、力或状态变化更容易与几何规划和控制约束对接，但建模成本较高

视频看起来合理，不代表预测的物体位置、接触时刻和受力正确。若 Agent 要用预测结果决定“向左拉还是向前拉”，模型输出就必须与这些动作选择有关，并能通过真实执行验证。一个可用的 World Model Skill 应明确预测对象、时间范围、动作条件、坐标系、置信度和适用边界。

5.2 从单步预测到候选动作评估

假设开门时有三个候选动作：沿门法向拉、沿把手切向拉、先调整底盘再拉。World Model 接收当前状态与候选动作，预测未来状态。Agent 不能只选“模型生成视频最漂亮”的一个，而应根据任务进度、碰撞、接触稳定性和不确定性计算效用。

pred = world_model.rollout( state=world_state, candidates=[ Action("pull", direction=door_normal, distance=0.08), Action("pull", direction=handle_tangent, distance=0.08), Action("reposition_base", offset=base_offset) ], horizon=12 ) for candidate in pred: candidate.score = ( 2.0 * candidate.expected_door_angle - 3.0 * candidate.collision_risk - 1.5 * candidate.contact_loss_risk - 1.0 * candidate.uncertainty ) best = max(pred, key=lambda x: x.score)

这个评分只是教学例子，系数必须通过任务目标和实验确定。它说明 World Model 并不直接替 Agent 做全部决策：模型给出未来预测，Agent 把预测映射到任务效用和约束，再选择动作或技能。若候选方案之间差异小于模型不确定性，就不应把分数最高者当作可靠结论。

5.3 模型不确定时，Agent 应该先观察，而不是硬选动作

预测误差可能来自视觉状态估计错误、训练分布外场景、接触参数未知或动作执行偏差。Agent 可以采用简单的决策规则：若候选动作的预测优势明显且不确定性低，则执行；若预测分歧大，则调用主动感知；若所有候选都风险高，则换站位或请求人工帮助。

if prediction_uncertainty < low_threshold: execute(best_candidate) elif prediction_disagreement > disagreement_threshold: call_skill("active_perception") else: call_skill("reposition_or_replan")

5.4 World Model 不一定是一个大模型

在机器人任务中，World Model Skill 可以是学习式视频/潜空间模型，也可以是辨识出的门轴模型、刚体几何、接触模型或简化动力学。Agent 关心的是“它能否回答当前决策所需的问题”，而不是它是否使用 Transformer。已知门轴的开门任务可能用几何模型更可靠；陌生柔性物体则可能需要学习式预测。

建议的最小验证：固定一批当前状态与候选动作，比较预测位姿/接触事件与真实执行结果；按预测置信度分桶，检查高置信样本是否真的更准确；再做消融，确认 Agent 加入 World Model 后减少了失败或无效尝试，而不只是增加推理时间。

06Code-as-Policy：让 Agent 写出的程序成为可复用技能

Code Policy 的价值不在于“LLM 能写 Python”，而在于程序可以被检查、组合、复用、参数化和版本化。它把一次任务推理沉淀成后续能够直接运行的控制逻辑。

6.1 代码为什么可以成为 Policy？

传统 Policy 通常写成 a_t = π(o_t, g)，输入观测和目标，输出动作。Code Policy 则是一个程序 P：它读取状态、调用可用工具、根据条件分支、循环执行，并在满足终止条件时返回。程序中可以包含一个神经网络 Policy，也可以组合几何算法、MPC 和恢复逻辑。

def open_drawer(state, tools, params): handle = tools.localize_handle(state.image) pregrasp = tools.compute_pregrasp(handle, params.offset) tools.move_to(pregrasp) contact = tools.verify_contact() if not contact: return {"status": "needs_replan", "reason": "no_contact"} while tools.observe_door_angle() < params.target_angle: tools.compliant_pull(params.pull_step) if tools.force_limit_exceeded(): return {"status": "failed", "reason": "force_limit"} return tools.verify_drawer_open()

程序的控制流是显式的：先定位，再接近，再检查接触，再循环拉门。它可以被人阅读和调试，也可以把 params.pull_step 作为可优化参数。缺点是代码可能脆弱、依赖环境假设，或在生成时遗漏安全分支；因此代码生成不等于策略已经可靠。

6.2 代码进化与参数进化是两件事

假设开门失败。若失败原因是拉门步长过大，可以只改参数；若失败原因是接触后没有重新估计门角，需要修改程序逻辑；若视觉表征无法识别新型把手，才可能需要替换感知模型或训练模型。把所有失败都交给 LLM “重写整个程序”，会破坏已经有效的部分，也很难定位性能变化来自哪里。

进化对象修改内容验证重点
参数阈值、步长、速度、抓取偏移参数范围、灵敏度、跨场景稳定性

6.3 经验记录应该包含什么？

只保存“成功/失败”不足以支持改进。一个可检索的 Experience 至少应绑定任务条件、场景摘要、程序版本、关键状态、工具调用序列、环境回执、终止原因和适用范围。失败记录尤其要保存失败发生在哪个阶段，以及执行前提是否满足。

Experience = { task: "open_drawer", context: { handle_type: "horizontal_bar", hinge_side: "left", base_distance_m: 0.46 }, policy_version: "open_drawer_v12", trace: [ {"step": "localize_handle", "status": "ok"}, {"step": "approach", "status": "ok"}, {"step": "establish_contact", "status": "failed"} ], outcome: "failure", failure_code: "contact_slipped", evidence: { peak_force_n: 18.2, door_angle_change_deg: 1.4 }, lesson: "approach pose too lateral for this handle family" }

检索时不能只按任务名称匹配。两个任务都叫“开门”，但门轴方向、把手形状、底盘站位和接触方式不同，可能需要不同策略。可先用结构化元数据筛选，再用文本/向量相似度检索经验，最后由 Agent 判断哪些经验可迁移。

6.4 一个真正的候选版本晋升流程

进化系统应维护稳定版本 P_v 和候选版本 P_{v+1}。候选版本在固定场景集上与基线配对评估，记录成功率、失败类型、耗时和安全约束。只有候选在目标指标上有可信收益，且没有明显损害关键护栏，才晋升为默认版本。

baseline = load_skill("open_drawer", version="v12") candidate = revise_code( baseline=baseline, experiences=retrieve_failures("contact_slipped"), instruction="change only the approach/contact recovery logic" ) static_check(candidate) interface_test(candidate) sim_results = paired_eval( skills=[baseline, candidate], seeds=heldout_seeds, scenarios=heldout_drawers ) if (sim_results.success_rate_gain >= min_gain and sim_results.safety_violations == 0 and sim_results.regression_on_core_cases <= max_regression): promote(candidate) else: archive(candidate, reason=sim_results.summary)

固定场景集用于控制比较噪声，Held-out 场景用于检查泛化。不能只在 Agent 刚刚失败的那个场景上反复调到成功，然后就宣称技能变强。还应保留旧版本、生成差异、评估记录和回滚路径。

07Coding Agent 工具与 Runtime：让 Agent 能开发、调试和维护 Skill

有必要学习，而且它是 Code Policy Evolution 的基础设施。RAX 使用 Coding Agent Harness 驱动机器人探索；RoboScript 也把 Actor、Reviser、工具 Hub 和任务记忆分开。你需要理解的不是某个 CLI 的快捷键，而是 Coding Agent 如何通过一组通用工具，把“修改程序”变成可观察、可验证、可回滚的工程闭环。

先区分两套工具：Coding Agent 工具用于理解和修改 Skill 的代码与工程；Robot Agent 工具用于感知和改变物理世界。前者可以生成或维护后者，但不应因为 Coding Agent 有 Shell，就让它绕过机器人 Runtime 直接控制硬件。

7.2 最小工具集与进阶工具集

对你的机器人技能开发，最小可用集合其实不大：读取/搜索文件、精确编辑、执行命令、查看长进程输出、运行测试、查看 Git Diff。缺少其中任何一类，Agent 都容易退化成“生成代码后让人手动检查”。

进阶能力包括 Browser/MCP、Sub-agent、长期 Memory、工作区快照、并行仿真和资源调度。它们不是第一天就必须全部部署的功能；只有在任务确实需要跨仓库研究、并行诊断、调用外部服务或管理长时运行时才增加。

7.3 Coding Agent 的 Harness：工具不等于 Agent

一个 Coding Agent 系统至少包含四个不同部分：模型负责提出下一步工具调用；Harness 维护对话、上下文和工具循环；Workspace/Sandbox 提供文件系统与进程执行环境；工具执行器真正完成读写、命令和测试。模型本身通常不直接访问文件系统或操作系统，而是请求 Harness 执行工具，再根据工具结果继续推理。

while not finished: context = assemble( task=goal, repo_state=workspace.summary(), history=compact(history), tool_schemas=registry.schemas() ) call = model.next_tool_call(context) # Harness 校验工具、路径、参数和权限 request = policy.validate(call) # Workspace 在受限环境中执行 result = sandbox.execute(request) history.append(call) history.append(result) if result.changed_files: update_workspace_index() if call.is_terminal: finished = True

这说明工具能力、模型能力和执行环境是三个独立变量。换更强的模型不自动带来更安全的文件权限；增加更多工具也不自动让 Agent 更聪明。真正的能力来自模型、工具描述、上下文组织、执行反馈和 Runtime 约束的共同设计。

7.4 把 Coding Agent 接入机器人项目时，必须增加的边界

  • Workspace 隔离：Agent 修改的是候选工作区或 Git Worktree，不直接覆盖正在运行的机器人版本。
  • 命令与资源预算：限制 GPU、仿真并发、运行时长、磁盘和网络访问；长进程必须可查看和终止。
  • 权限分层：读取日志、修改代码、运行仿真、连接真机应是不同权限级别。真实机器人动作不能仅因为 Shell 可用就自动获得。
  • Secrets 隔离：API Key、SSH 私钥和机器人凭据由执行环境注入，不能写入 Prompt、日志或生成代码。
  • 验证后晋升：候选 Skill 先通过静态检查、接口测试、仿真和回归评测，再进入稳定 Skill Registry。
  • 可追溯：保存模型版本、Prompt/任务上下文、工具调用、文件 Diff、测试结果和最终晋升决定。

7.5 一次完整的 Code Policy 修改循环

关键点是把“代码修改”与“部署晋升”分开。Coding Agent 可以提出候选修改，但是否晋升由独立评估规则决定。对探索期可以降低流程复杂度，但不能省略最基本的回归测试和旧版本保留。

Working Memory当前任务进行到哪里？子目标、当前假设、待办、活动 Skill 状态任务/会话期间
Episodic Memory以前具体发生过什么？观测摘要、工具调用、动作回执、成功/失败轨迹长期保存，可按需检索

Procedural Memory / Skill Library已经学会怎样完成某件事？可执行 Skill、Policy、参数、依赖和验证器版本化，需评测后晋升
Database / Storage如何可靠保存、索引、查询上述信息？关系表、向量索引、对象文件、事件日志由存储策略决定

关键点：数据库不是记忆本身，而是承载记忆的存储与检索基础设施；Context 也不是长期记忆，只是本轮从任务状态和存储中挑选出来的有限信息。把整个聊天记录塞进 Prompt，既昂贵也不可靠。

8.2 常见记忆类型与机器人例子

  • 工作记忆（Working）：当前打开柜门任务的阶段、已估计的门轴、当前接触状态、活动 Skill ID 和剩余预算。必须快速读写，任务结束后可以归档。
  • 情景记忆（Episodic）：某一次柜门操作的完整事件：当时的场景、程序版本、调用过哪些工具、力觉曲线、门角变化和最终结果。它是事后分析与相似案例检索的证据来源。
  • 语义/任务记忆（Semantic / Task）：“左侧铰链门通常沿圆弧运动”“某类把手需要先建立侧向接触”等归纳知识。它应附带来源、置信度、适用条件和最后验证时间，不能把一次偶然成功直接升级为通用规则。
  • 程序性记忆（Procedural）：已验证的 open_door_v13 Skill、它的输入输出 Schema、适用机器人、依赖模型和评测结果。它不是自然语言经验，而是可被 Runtime 调用的能力版本。
  • 用户/项目偏好记忆：例如特定机器人平台、常用坐标约定或项目配置。它与任务成功经验不同，需要独立权限和更新策略。

8.5 一次“查询相似失败经验”的完整流程

假设当前开门 Skill 在接触后打滑。Agent 不应该只搜索“开门”两个字，而应先抽取结构化条件：任务类型、把手形状、接触阶段、底盘距离、失败码和机器人本体。先用 SQL 做精确过滤，再用向量检索对失败描述和场景摘要排序，最后读取少量原始轨迹核实原因。

# 第一步：结构化筛选，数据库只返回允许字段 candidates = db.query( """SELECT episode_id, skill_version, failure_code, handle_type, base_distance, summary_uri FROM episode_index WHERE task_type = :task AND robot_family = :robot AND failure_code = :failure ORDER BY created_at DESC LIMIT 100""", params={ "task": "open_door", "robot": "mobile_manipulator", "failure": "contact_slipped" } ) # 第二步：对候选摘要做语义召回与重排 similar = vector_index.search( query=current_failure_summary, filters={"episode_id": [x.episode_id for x in candidates]}, top_k=5 ) # 第三步：只读取最相关的证据，再决定是否迁移经验 evidence = artifact_store.read_episodes(similar.ids) proposal = agent.propose_skill_update(evidence)

这个流程是 Hybrid Retrieval：结构化过滤负责精确约束，向量召回负责语义相似，重排/证据读取负责判断可迁移性。向量相似度高不等于物理条件相同，最终仍要核对坐标系、机器人本体、物体几何和任务前提。

8.6 Memory 写入比 Memory 读取更需要设计

如果每次对话、每个工具结果都直接写进长期记忆，数据库很快会充满重复、矛盾和过时信息。建议把写入分成三层：

  1. 原始记录（Raw Trace）：工具调用、观测引用、回执和时间戳尽量追加保存，作为可追溯证据，不让模型任意覆盖。
  2. 候选总结（Candidate Memory）：Agent 从多次 Episode 中提出规律，明确支持证据、反例、适用条件和置信程度。候选总结可以被修订，但不能直接当成稳定知识。
  3. 稳定记忆（Curated Memory）：通过重复验证、人工审核或自动评测门槛后，才更新共享 Task Memory 或 Skill Registry，并保留版本和回滚路径。

一条经验升级为长期规则，至少要回答：它来自多少次独立执行？有没有反例？适用哪些场景？是否跨机器人/物体泛化？最后一次验证是什么时候？如果证据不足，应保存为“候选假设”，而不是确定事实。

8.7 Context 管理：摘要、压缩与检索不是同一件事

长时序任务会产生大量图像描述、工具输出和推理历史。Context Window 是有限工作区，不能无限保留所有内容。常见策略包括：保留最近几轮原始交互；将较早过程压缩为结构化摘要；把大图像/轨迹放在 Artifact Store，只向模型提供引用；在需要时从 Episodic Memory 重新检索证据。

摘要可能丢失细节，因此关键事实（成功回执、物体位姿来源、失败码、版本号、坐标系、用户约束）应以结构化状态或可追溯记录保存，而不是只存在于自然语言摘要里。Context compaction 是上下文管理，不能代替长期记忆；RAG 是检索相关信息，也不能自动保证记忆正确。

8.8 一个适合你的最小记忆数据模型

Task( task_id, goal, robot_family, created_at, status ) Episode( episode_id, task_id, scene_tags, skill_version, outcome, failure_code, started_at, duration ) Event( event_id, episode_id, seq, event_type, tool_name, input_ref, result_ref, timestamp ) MemoryItem( memory_id, scope, content, evidence_episode_ids, confidence, applicability, status, version ) SkillVersion( skill_id, version, artifact_uri, interface_schema, dependencies, eval_report_uri, lifecycle_status )

这不是要求你一开始就建五张生产级数据库表，而是先明确数据实体与关系。尤其要把 Episode、Event、MemoryItem 和 SkillVersion 分开：一次经历是证据，一条记忆是对证据的总结，一个 Skill 版本是可执行产物。

本节核心结论：你的 Agent 至少需要“结构化数据库 + 文件/对象存储 + 可选向量检索 + 事件轨迹 + 版本化 Skill Registry”。先从 SQLite/PostgreSQL 和本地 Artifact Store 做最小实现，等检索规模、并发或关系复杂度真的成为瓶颈，再增加专用数据库。

10持续进化不只有改代码：RAX、Voyager 与 RoboScript 的三种记忆

这三个项目值得放在一起比较，因为它们沉淀的“经验”并不是同一种东西。理解差别，才能选择你的系统应该改程序、改任务记忆，还是改模型。

系统主要沉淀进化方式适合解决
Voyager可执行代码技能库生成、执行、根据错误迭代并检索技能技能逐步积累与组合
RAX代码、技能与完整交互轨迹Coding Agent 在线探索，利用环境反馈改进程序机器人任务的自主探索与程序技能获取
RoboScript / WICL结构化 Task Memory从示教形成记忆，在练习失败后修订，冻结后评测把任务流程、对象角色和参数迁移到新场景

7.1 Voyager：技能库如何复利增长？

Voyager 的关键不只是让 LLM 写代码，而是把技能存为可执行程序，并建立自动课程与技能检索。新任务到来时，Agent 可以先检索已有技能作为上下文，再生成组合或扩展程序；执行错误和环境反馈进入下一轮修改。技能因此具有时间抽象和组合性，后续任务不必每次从零开始。

但 Voyager 运行在 Minecraft，动作 API、环境状态和成功条件都比真实机器人容易访问。迁移到机器人时，需要把游戏中的直接 API 调用替换成有权限边界的 Robot Tool，并增加物理执行验证、实时控制和安全约束。它提供的是持续技能学习机制，不是可直接部署的机器人控制栈。

7.2 RAX：Coding Agent 与机器人 Harness 的边界

RAX 特别值得看的是它把三件事分开：Coding Agent Harness 负责模型对话、工具调用和会话历史；RAX 提供机器人工作区、观察/控制接口、探索预算和评测；模型 Provider 负责推理服务。这样同一个机器人实验环境可以更换 Codex、Claude Code、DeepSeek Harness 或 Kimi Code，而不必把模型供应商和机器人接口耦合在一起。

阅读 RAX 时，先不要只看生成出的 skill.py。应追踪一次完整 session：Agent 收到哪些图像和状态、有哪些工具、工作区能访问什么、代码在哪个隔离环境运行、执行错误如何回传、探索预算如何限制、最终评测如何独立启动。RAX README 说明代码按 benchmark/hardware 分支组织，main 是索引；阅读时要进入对应分支，而不是只读主分支。

7.3 RoboScript：把任务知识从模型权重中拆出来

RoboScript 的 WICL 将任务学习分成 imitate、practice 和 evaluate。Demo Reader 从一条示教写出初始 Memory；Actor 使用 Memory 尝试任务；Reviser 在失败后编辑 Memory；practice 阶段换到新场景继续练习；最终冻结 Memory 并在官方评测集运行。Memory 是 Markdown 任务说明加结构化参数，不是模型权重，也不等于完整可执行程序。

它还有一个重要边界：练习/评测时 Actor 看到部署级信息，但学习阶段某些角色可以读取仿真特权信息用于诊断。因此不能把结果描述成完全无特权学习。它的价值是把任务流程和参数显式化，并通过阶段化协议验证迁移能力。

7.4 你的系统应该怎样组合这三种记忆？

我建议至少分成三层：Task Memory 保存对象角色、任务步骤、完成条件和环境假设；Skill Library 保存可执行的代码/Policy 及版本；Episodic Experience 保存具体场景下的轨迹、回执和失败证据。三者通过 Skill ID、版本号和任务类型关联，而不是把所有东西都塞进一个向量数据库。

RobotAgentMemory/ task_memory/ open_door.md open_door.params.json skill_library/ open_door/ v12/ controller.py skill.yaml v13-candidate/ controller.py skill.yaml episodes/ open_door/ episode_000184.json episode_000185.json evaluations/ open_door/ v12_vs_v13.json

Agent 决策时先读任务记忆和 Skill Registry；执行失败时检索 Episode；若发现是流程知识错误就修改 Task Memory，若是程序逻辑错误就生成新 Skill 版本，若是模型感知/动作能力不足再考虑模型训练。这个分层能减少“什么问题都用微调解决”的倾向。

11真实项目代码拆解：OpenETA 的一次 Tool Call 如何走完

这里以 OpenETA 的公开架构文档和 Agent Command Pipeline 为例。它的价值不是证明某一种架构最好，而是展示如何把 Agent 决策、Tool Registry、模拟器边界和物理动作副作用分开。

8.1 从观察到命令：主链路

Observation + Task + Memory + Tool/Skill References | v ToolCallingPlanner | PlannerBackend (LLM) | structured decision | parse + schema validation | ActionPipeline | ToolRegistry | ToolResult / Receipt | Memory + updated observation | next Agent turn

OpenETA 的主 Planner 每轮只提出一个 tool_call 或 response。ToolCallingPlanner 把当前观测、任务、Memory 摘要、工具引用、Skill 元数据和执行规则组织成有限上下文；Planner Backend 返回结构化决策；Runtime 验证命令类型、工具名、参数和 Code Policy 限制；ActionPipeline 再把决策编译成 Tool 调用。

这里的关键不是 XML/JSON 格式，而是模型输出不能直接成为物理执行命令。中间必须有 Schema Validation、工具注册表、权限检查和执行合同。参数不合法时可以把错误反馈给模型重试，但重试次数、超时和最终回退由 Runtime 控制。

8.2 为什么 SAM 结果还不能直接进入抓取？

OpenETA 的工具列表包含 SAM3、候选选择、AnyGrasp、相机坐标到世界坐标转换和运动控制。SAM3 可能返回多个检测候选；Runtime 会要求显式选择一个稳定 Detection ID，不能让后续抓取规划绕过这一步。抓取网络返回的候选是带来源的证据，分数只是该后端内部的提示，不应直接当作跨模型可比较的成功概率。

抓取位姿还要带坐标系。相机坐标系下的点必须通过标定变换转到世界坐标系，再交给以世界坐标为输入的运动工具。若没有保留候选 ID、图像来源、标定版本和变换记录，后续即使机器人撞到了物体，也难以判断错误来自分割、候选选择、坐标转换还是运动规划。

8.3 为什么 Code Policy 只是可选 Backend？

OpenETA 的架构文档明确将 code_policy 作为 Tool Call 下的可选后端，而不是整项任务的主循环。它适合短时域、可局部验证、内部能够 checkpoint/observe 的代码片段；真实环境执行仍要通过受控 Tool 或 Simulator MCP 边界，不允许代码直接持有原始环境对象并绕过 Runtime。

这和 RAX 的设计形成有价值的对照：RAX 的核心探索方式就是让 Coding Agent 在隔离工作区内编写、执行和改进程序；OpenETA 则更强调主 Agent 的逐步闭环 Tool Call，以及 Host 对物理动作的控制。前者适合研究“程序如何通过探索学出来”，后者适合研究“程序如何在受控 Runtime 中安全执行”。两种思想可以组合，但不能把它们的执行权限和评测协议混为一谈。

8.4 源码阅读任务

  1. 打开 Agent Command Pipeline，画出 Planner 到 ToolRegistry 的调用链。
  2. 打开 Architecture，标出哪些模块掌握模拟器真值、哪些模块只看到 Agent-facing Observation。
  3. 追踪一次 SAM3 调用：输入图像引用、检测结果、候选选择、AnyGrasp、坐标变换和 move_to。
  4. 检查 world-mutating Tool 的执行后是否强制刷新 Observation；对照只读工具的批量调用规则。
  5. 找出 ToolResult 与独立环境成功判定之间的差别，解释为什么 Tool 返回成功不等于任务成功。

12怎样判断 Agent 真的变强了？

Robot Agent 不能只看最终成功率。否则你无法知道改进来自更好的任务决策、更强的 VLA、更稳定的控制，还是更多的尝试次数。

层级核心指标要回答的问题
Agent 决策Skill 选择准确率、无效调用、重规划次数、决策延迟是否选对能力？是否过度调用大模型？
Skill 执行子目标成功率、超时率、恢复成功率、调用成本技能是否可靠且可组合？
VLA / Policy动作误差、Chunk 连续性、闭环成功率、时延执行策略是否稳定？
World Model状态预测误差、排序准确率、校准误差预测是否能帮助选动作？
持续进化新场景成功率、回归率、版本晋升率、遗忘经验是否带来可迁移的能力增长？
系统整体任务成功率、耗时、人工介入、安全违规用户目标是否更可靠地完成？

9.1 至少做四组对照

  • 固定 Skill、不同 Agent：隔离决策能力，比较不同 Planner 是否选出更合适的技能。
  • 固定 Agent、不同 Skill：隔离执行能力，比较 VLA、Code Policy 和传统控制器。
  • 有无 Memory / World Model：测量额外认知能力是否真正减少失败和尝试。
  • 旧版本与新版本配对测试：固定任务、种子和场景，评估 Skill Evolution 是否带来可重复收益。

评测要同时报告 Pass@1 和有预算限制的 Pass@k。Pass@k 允许多次尝试，不能与单次执行成功率直接比较；如果尝试间有人类修改 Prompt、代码或参数，还必须明确标注人类介入。最好使用固定预算、盲测场景和独立成功判定器。

9.2 持续进化的核心指标

我建议增加一个“经验收益曲线”：横轴为累计交互次数或探索预算，纵轴为未见场景成功率。同时画出无记忆、仅任务记忆、代码技能库、完整进化系统。还要跟踪旧任务回归率，防止新任务提升是以旧技能退化为代价。

真正的持续进化不是“每次失败后都生成一个新版本”，而是在固定资源预算下，随着经验增加，未见任务的表现持续改善，并且旧任务能力没有不可接受的回退。

13学习路线：从 Agent 决策到持续进化

建议按下面顺序学习。每一部分都围绕一个系统问题展开，避免把课程变成零散术语清单。

  1. Agent Loop 与任务级决策 P0

    Observe–Reason–Act–Verify；任务状态、目标分解、工具调用、终止条件；快速路径与深度推理的触发机制。重点回答 Agent 如何决定“下一步做什么”。

  2. Skill 抽象、接口与层级组合 P0

    Skill Contract、输入输出 Schema、前置条件、后置条件、超时、取消、状态反馈；Skill 可以嵌套子 Skill，也可以包含完整 Policy 和控制器。

  3. 长时序 VLA：作为执行型 Skill P0

    VLA 的长时序任务封装、动作块滚动执行、RTC / Receding Horizon、子目标检测、执行监控、终止与恢复。Agent 调用一次技能，不必逐 Chunk 指挥。

  4. World Model：作为预测与评估 Skill P0

    状态预测、动作条件未来预测、候选动作评估、反事实推演、模型不确定性。学习 Agent 何时值得调用世界模型，以及如何把预测结果转成决策依据。

  5. 感知与几何工具链 P1

    VLM / SAM 分割、开放词汇检测、深度估计、2D-to-3D、场景图、抓取位姿和运动规划。重点是理解工具输出如何变成可供 Agent 使用的 World State。

  6. Code-as-Policy 与程序生成 P0

    从自然语言目标生成可执行程序；程序结构、API 约束、参数化控制、子程序复用；把生成的程序封装成有明确契约的 Skill。

  7. 经验记忆与 Code Policy Evolution P0

    记录轨迹、状态、工具调用、失败原因和结果；检索相似经验；对现有程序做局部修改、组合或替换；在仿真/受控环境中评估，再晋升版本。

  8. Meta-policy 与系统集成 P1

    学习何时调用哪种 Skill、何时探索、何时复用；技能发现、技能淘汰、多 Agent 协作；最终构建可观测、可验证、可持续改进的 Robot Agent。

15代码阅读顺序

不要从头到尾通读仓库。每个项目都按同一组问题追踪一次真实任务：

  1. 入口在哪里？任务上下文和环境观测如何进入 Agent？
  2. Agent 的决策循环在哪里？如何判断继续、等待、结束或重规划？
  3. Skill / Tool 如何注册？参数和返回值有哪些约束？
  4. VLA 或其他 Policy 如何作为一个可持续运行的执行单元？
  5. 环境变化如何验证？工具成功与任务成功如何区分？
  6. 轨迹、错误和经验保存在哪里？如何检索？
  7. Code Policy 如何生成、修改、测试、版本化和晋升？

推荐顺序：先读 OpenETA 理解物理闭环与执行边界；再读 RAX 理解在线探索和代码技能进化；对照 RoboScript 理解任务记忆如何在不改模型权重的情况下持续优化；再读 Voyager 理解技能库与长期积累；随后读 Q0-Preview 和 HoloAgent-0，比较空间推理与空间记忆路线。

16综合实战：持续进化的开门 Agent

以你熟悉的柜门/抽屉操作为主线，不必从便利店通用任务开始。这个任务能同时考察几何、接触、长时序执行、模型预测和技能改进。

User goal: 打开陌生柜门并取出目标物体 Agent: 1. 读取 World State 与历史技能 2. 检索相似柜门的 open_door Skill 3. 若信息不足，调用 Perception / World Model 4. 选择 VLA Skill 或 Code Policy 执行 5. 在子目标处检查门角、接触力和任务状态 6. 失败时定位原因并选择恢复方案 7. 验证任务结果 8. 将新经验写入候选 Skill 版本 9. 离线评估通过后更新 Skill Library

建议消融：无记忆；加入经验检索；加入 World Model 预测；加入长时序 VLA Skill；加入 Code Policy Evolution；完整系统。分别测任务成功率、重规划次数、人工介入次数、完成时间、安全违规和跨柜门泛化。
