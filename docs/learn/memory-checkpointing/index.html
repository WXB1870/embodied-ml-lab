训练显存用于保存参数、梯度、优化器状态、激活和临时数据等对象。激活检查点（Activation Checkpointing）是一种少保存部分前向中间值、反向时重新计算它们的方法，以额外计算换取内存；它不同于把训练状态保存到磁盘的 checkpoint。本章先建立内存账目，再认识冻结、重计算和对象寿命，最后同时检验节省量与计算一致性。

前置知识：PyTorch 自动微分与计算图 · 混合精度训练

本章学习目标

  • 按参数、梯度、优化器状态和激活拆解训练内存。
  • 正确使用非重入 activation checkpoint 并核对梯度。
  • 区分逻辑保存量、实际张量内存与缓存预留内存。

01训练内存由哪些对象组成

训练内存账目是按对象与生命周期统计当前计算需要保存哪些数值。常驻参数状态、反向激活和临时工作区有不同来源，因此需要不同节省方法。先分清对象，再估算参数数目以外的成本。

训练内存至少包括参数、梯度、优化器状态、为反向保存的激活、当前输入输出和算子临时工作区。若参数、梯度和 Adam 的两个矩都以 FP32 保存，仅这四项就约为 16P 字节，其中 P 是参数数目。这个估算不包括激活、临时张量、通信缓存或实现额外副本，因此不能用参数量乘固定系数直接保证模型一定装得下。

例：一个明确假设下的状态内存估算

  1. 假设 P=100 万，参数、梯度、一阶矩、二阶矩都为 FP32，且没有其他副本。
  2. 每类约 4 MB，四类合计约 16 MB（十进制）。
  3. 前向激活、Batch、临时工作区和框架开销还需另外计算。

16P 是这组假设下的状态估计，不是普遍的训练峰值公式。

混合精度、分片优化器、参数冻结和融合内核会改变各项构成。有的配置保留 FP32 主参数，有的以 FP32 参数执行 autocast；二者不能重复或遗漏计数。估算时为每一类对象列出元素数、dtype、是否常驻和是否被分片，再对照实际测量。模型文件大小只对应保存格式，不等于峰值训练内存。

内存单位也要保持一致：MB/GB 按十进制，MiB/GiB 按二进制，工具显示口径可能不同。容量规划还需为峰值波动与运行时开销留余量；不能用四舍五入后的理论估计刚好贴满设备容量，再把偶发 OOM 归为不稳定。

02激活为何随 Batch、序列和宽度增长

激活是前向产生的中间表示，自动微分还可能保存其中部分数据供反向使用。它的规模由批量、序列、宽度和具体算子共同决定。下面沿张量而非模型文件大小估算这部分内存。

一个 [B,T,D] 激活包含 BTD 个元素；同一网络中还可能有多个投影、中间 FFN、归一化和反向所需保存量。标准显式注意力分数为 [B,H,T,T]，序列长度翻倍会让这一个张量元素数约增四倍。使用不显式保存完整矩阵的优化算法可以改变实际内存行为，所以应同时区分数学计算复杂度和具体实现的保存策略。

增大图像分辨率、相机数或历史长度通常增加 token 数，从而影响后续多个模块。仅在最后增加一层小 MLP，新增参数可能不多，但前面的长序列激活仍是主要成本。减少微批大小主要降低激活峰值，不能消除常驻优化器状态；反之，LoRA 减少可训练参数状态，也不一定显著减少所有激活。

读内存问题时应先判断随哪一项配置增长：Batch 线性增长提示激活，参数数量变化提示状态，某段序列长度引起突增可能涉及注意力或临时工作区。这些只是定位线索，最终仍需逐阶段测量。

03冻结能够省掉什么，不能省掉什么

冻结参数可免去其梯度和相应优化器状态，但不自动移除前向权重或求输入梯度所需的激活。是否能停止建图取决于上游还有没有可训练对象。下面按求导路径区分这些成本。

冻结参数通常无需为这些参数保存梯度和对应优化器状态，但其权重仍需参与前向。如果冻结模块之前还有可训练 Adapter，反向仍需要穿过它来计算输入梯度，相关激活不一定能全部省去。只有在没有必要上游梯度的边界停止建图，才可以避免该区域的反向保存；不恰当地使用 no_grad 会直接改变可训练路径。

参数冻结也不自动把模块切换到 eval，Dropout 或 BatchNorm 行为与梯度设置独立。离线缓存固定特征可能进一步减少训练计算，但它要求输入预处理、随机增强、条件和编码器状态都满足缓存有效性条件。缓存来自未来信息或不一致增强时，内存节省的同时改变了训练问题，应独立审查。

可训练参数少就认为激活内存必然很小

反向是否经过大骨干由计算依赖决定，不只由骨干参数 requires_grad 决定。

检查：画出可训练模块的位置，分别测冻结、停止建图和真正裁断前置梯度的影响。

04allocated、reserved 与峰值测量

allocated 统计活跃张量等已分配内存，reserved 还包含缓存分配器为复用而保留的内存块，峰值则记录某区间的最高占用。它们是不同测量口径。先固定口径，再判断内存增长与释放。

设备内存的已分配量通常指仍被活跃张量占用的部分，缓存分配器预留量还包含可复用的内存块。预留量高不等于全部都是泄漏；调用 empty_cache 可以释放部分空闲缓存给其他使用者，却不能释放仍被张量引用的内存。把清缓存放进每个训练步，也可能增加分配开销而不解决活跃对象过大的根因。

峰值应覆盖完整训练步，并明确统计从什么时候开始。先预热模型，必要时同步设备，重置峰值统计，再测前向、反向和 step；优化器状态可能在第一次 step 才创建，所以只测前向会低估。计时同样需要处理异步执行，不能用 CPU 调用返回时间直接当作 GPU 运算耗时。

按阶段记录内存，而不是只看一张显卡截图

前向、反向和 optimizer.step 的峰值来源可以不同。

检查：在固定输入上分别记录 allocated/reserved/peak，并说明预热、同步与首次状态创建。

05激活重计算用额外计算换取更少保存量

激活重计算是在反向需要中间量时，重新执行选定前向区段来恢复它们的机制。它减少保存量，却要求重算仍对应原来的函数。先看保存与重算怎样配合，再讨论区段选择。

普通反向需要某些前向中间值，激活 checkpointing 选择只保存区段边界等必要信息，在 backward 时重新执行部分前向来恢复中间量。它不会从磁盘读取 checkpoint，也不等于训练断点保存；两者名称相近，但用途不同。被重计算的函数必须在两次执行中代表同一个计算，否则输出或梯度可能改变。

例：为什么保留边界仍能反向

  1. 设一段计算 x→h1→h2→yx\to h_1\to h_2\to yx→h1​→h2​→y⁠，普通反向可能保存 h1h_1h1​ 与 h2h_2h2​⁠。
  2. 重计算策略保存 x 和必要状态，反向需要 h1 / h2h_1\text{ / }h_2h1​ / h2​ 时再从 x 重做这段前向。
  3. 节省的是部分中间保存，增加的是再次求值；x、参数、梯度与优化器状态仍要存在。

激活重计算改变保存策略，不改变期望优化的数学函数。

PyTorch 提供不同重计算实现，示例显式使用 use_reentrant=False，避免依赖默认选择。分段长度越大，保存边界可能越少，但需要重算的工作也可能更多；实际实现还可能提前停止已不需要的重算。选择区域应根据激活成本、计算成本和依赖关系，不能假定包住整个网络就获得最佳时间—内存折中。

重算的收益取决于哪些中间量本来需要保存。一个几乎不保存大激活的廉价算子，包住后可能只有管理开销；含大型中间投影的块则可能收益明显。先用保存量和 profiler 定位，再选择分段，能够避免把更多计算花在没有实际内存节省的位置。

06随机状态与副作用是重计算的高频陷阱

随机状态决定 Dropout 等随机计算的结果，副作用是函数对返回值之外状态的修改。重计算会再执行前向区段，因此两者都可能使它偏离原计算。需要定义哪些状态被保留或再次更新。

如果区段包含 Dropout，重算必须采用与原前向相容的随机结果，才能恢复相同函数；框架通常提供随机状态保留机制，但跨设备、特殊随机源或自定义实现仍需核验。一个函数在前向时增加全局计数、更新外部缓存或改变隐藏状态，重算可能再次执行副作用，不能把它视为纯函数。

BatchNorm 运行统计、依赖全局变量的分支和在区段中迁移设备，都可能让第二次求值与第一次不同。默认一致性检查未必逐元素比较完整数值，不能把“不报错”当作严格等价证明。对计划重计算的模块，固定权重与输入，对照输出、每个参数梯度、必要的输入梯度以及状态 buffer，才能发现静默偏差。

包进 checkpoint 后只检查输出形状

状态副作用或随机差异可能保持相同 shape，却改变反向结果。

检查：对照无重算与重算路径的数值、逐参数梯度和状态变化；避免不可重入副作用。

07内存增长可能来自对象生命周期

对象生命周期决定一个带图张量何时仍被引用、其相关存储何时可被释放。持续保存损失或激活可能延长整段计算图寿命。下面区分必要日志、快照与不必要的图引用。

把 loss、预测或带图激活不断放进列表，会让其引用链延长，某些保存对象无法及时释放。日志应保存 item 或 detach 后的必要摘要；若还需要长期保留数据，明确拷贝到合适设备并控制容量。hook 闭包、异常 traceback 和缓存字典也可能持有大 Tensor，不能只检查显式的训练变量。

原地操作、del 和 empty_cache 都不是通用修复。del 只移除一个引用，其他对象仍持有同一存储时不会释放；视图可能共享大张量存储，保留一个小切片也可能间接保留原数据。连续运行相同形状步骤，观察峰值是否稳定，再逐项关闭日志和缓存，是区分常驻峰值与持续增长的有效对照。

08验证节省量时同时验证计算保持

保存量减少并不自动说明方案可用，梯度改变或重算耗时过大都会影响训练。以同一模型和数据为参照，同时核验计算结果、实际峰值及完整步耗时，才能解释获得的资源收益。

配套代码使用 saved_tensors_hooks 统计为反向保存的逻辑字节，比较普通路径和重计算路径的输出及参数梯度。这个计数不是 CUDA 峰值：同一存储可能被多次逻辑保存，临时工作区与缓存分配器也不在同一口径。CPU 示例能验证保存策略与梯度关系，不能直接声称节省了某个比例的真实 GPU 显存。

在目标硬件进一步评估时，应比较相同 Batch、序列形状、精度和模型模式，记录完整 step 的峰值、耗时和吞吐。选择收益明确且状态简单的区段，逐步增加覆盖，不要同时改变 Batch 和重计算区域后把所有差异归因于一种技巧。若内存瓶颈主要是优化器状态，激活重计算的收益也会有限。

最终方案可能组合较小微批与累积、混合精度、激活重计算和参数状态分片。每项策略都针对不同内存项，先定位再组合，才能解释资源收益及额外通信、计算和实现复杂度。

检查梯度保持时最好比较全部参数，而不只看最终输出或总范数。重算若在某个分支漏掉依赖，输出可能仍完全相同，却让一个子模块梯度错误。若输入前面有可训练模块，还需同时检查输入梯度，这一点与冻结模块的反向边界相通。

记录节省量时同时报告额外耗时，避免只展示内存下降。若重算让每步时间明显增加，应按相同墙钟或同等训练预算比较实际收益，并说明采用哪种预算。

训练内存优化先问对象在哪里产生、必须保留到何时，再选择冻结、分块或重计算。重计算真正交换的是保存量与计算工作；节省多少和是否仍计算同一目标，应使用各自口径验证。
